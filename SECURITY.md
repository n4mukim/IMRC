# IMRC blog · security and launch checklist (step 6)

## What is already enforced in code
| Layer | Protection | Checked by |
|---|---|---|
| Database | RLS on every table; roles re-read from `profiles` via `auth.uid()`; guard triggers; column-level grants; every `SECURITY DEFINER` function pins `search_path`; helper functions (`_name`) not callable by clients; views read-only | `app/tests/*` (127 tests, incl. `step6.security.test.ts` privilege snapshot) |
| Abuse limits | 5 submissions/day, 25 open drafts, 30 new drafts/day per author (tunable in `app_settings`); 200 images per account (`storage.sql`); 5 MB, image types only | step 3 + step 6 tests |
| Content | HTML allow-list on write (DB), on build (`blog_static.py`) and on render (DOMPurify) | step 3 tests, `test_blog_static.py` |
| Browser | Strict CSP (no inline script, no eval, no framing), HSTS, nosniff, Referrer-Policy, Permissions-Policy; SRI on pinned CDN scripts; JSON-LD escaped | `tools/test_security.py` + `tools/serve_with_headers.py` |
| Secrets | Only the public anon key is ever in `site/`; service-role key only in Edge Function env | `test_security.py` |

Run everything: `cd app && npx vitest run` · `python3 tools/build.py && python3 -m unittest tools/test_security.py tools/test_blog_static.py`

## Before launch (needs your Supabase / hosting accounts — I could not do these)
1. **Run migrations 0001–0008 in order, then `storage.sql`.** (0008 also closes a real gap: anon/authenticated had write grants on the `public_authors` view.)
2. **Auth settings** (Supabase → Authentication): enable CAPTCHA (Turnstile) and put the site key in `site/js/config.js`; require e-mail confirmation; minimum password length 12; leaked-password protection on; set Auth rate limits (sign-ups/sign-ins/OTP per hour) to conservative values; redirect URLs = your domain only.
3. **Admins use MFA** (Supabase → Authentication → MFA) and there are at least two admins.
4. **E-mail**: custom SMTP (Resend), SPF + DKIM + DMARC on the sending domain, then deploy `send-notifications` and `ban-user` and set `RESEND_API_KEY`.
5. **Backups**: enable daily backups / PITR; test one restore.
6. **Hosting**: deploy `site/` with `_headers` (Netlify/Cloudflare Pages) or `vercel.json` (Vercel) — both are generated by `tools/build.py`. Confirm with `curl -I https://culturalresilience.org/` that `Content-Security-Policy` is present. If you add a form service or analytics, set `EXTRA_CONNECT_SRC="https://your-form-host"` (and add script hosts in `tools/security_headers.py`) and rebuild.
7. **Contact / newsletter forms**: they post to a third-party form service — turn on its spam protection and rate limiting.
8. **Key hygiene**: rotate the service-role key if it was ever pasted anywhere; store it only in Supabase function secrets / CI secrets. `npm audit` before each deploy.
9. **Search engines**: submit `/sitemap.xml`; check Search Console for CSP-blocked resources in the first week.

## Known limits (honest list)
- Verified with PGlite (real Postgres) and a demo-mode UI — **not** against a live Supabase project, real e-mail delivery, Turnstile, or the hosting redirects.
- Google Fonts are loaded from Google (privacy trade-off); self-hosting them would let you drop two CSP hosts.
- CSP keeps `style-src 'unsafe-inline'` because pages use `style=""` attributes; scripts are strict.
- Turnstile's script cannot carry an SRI hash (Cloudflare changes it); it is limited by CSP host only.
- Client-side sign-in backoff is a convenience; the real limit is Supabase's server-side Auth rate limiting (item 2).
